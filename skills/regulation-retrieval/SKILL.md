# 税法检索与解读

## 使用场景

- 用户问某项业务的税务处理、适用税率、优惠条件、扣除标准
- 用户要求解释某条法规的含义或适用边界
- 用户问某个条款是否还有效、和旧版本有什么不同

## 工作流程

### 步骤 1：确认检索意图

从用户问题中提取：业务场景、税种、涉及主体（境内/境外、居民/非居民）、时间点。

用户表述含糊且不同理解会导致完全不同结论时（例如没说是境内还是跨境、没说居民企业还是非居民企业），**先问清再检索**，不要自行假设后直接作答。

### 步骤 2：检索条款

调用 `search_regulation`，用业务语言写 `query`，不要塞入法规文号。能确定税种时带上 `tax_category` 缩小范围。

- 返回 `NO_EVIDENCE`：换一种表述重试一次。仍然没有，就明确告诉用户"法规库中没有检索到相关条款"，**不允许用通用税务常识补答**。
- 一次检索不足以覆盖问题的多个方面时，分多次检索（例如零税率条件和免税情形分开查）。

### 步骤 3：取全文

`search_regulation` 返回的 `snippet` 是片段。只要结论依赖条款的具体数字、比例、期限或例外情形，**必须**用 `fetch_clause` 取回完整正文再下结论，不能只凭片段推断。

**检索时传了 `as_of` 的，取全文必须传同一个日期。** `fetch_clause` 不带 `as_of` 取的是最新版本正文——你检索命中的是当年那一版，正文却拿回现行版，两者结论可能完全相反，而且从返回值里看不出哪里错了。

### 步骤 4：作答

按下列结构组织回答：

1. **结论**：直接回答用户的问题
2. **适用条件**：逐条列出必须同时满足的条件
3. **例外与风险**：不适用的情形、容易踩的坑
4. **依据**：列出引用的条款号与标题
5. **待确认**（仅在存在时）：因信息不足无法判定的点

## 引用规则

- 每一句涉及法规事实的陈述，句末必须标注 `[clause_id]`，例如 `[AD-VAT-CN-00001]`
- **只能引用工具实际返回过的 clause_id**。不得凭印象拼造条款号或文号
- 一句话依据多个条款时并列标注：`[AD-VAT-CN-00001][AD-VAT-CN-00002]`
- 属于你的推断、类比或建议而非法规原文的内容，明确写成"这属于推断，需与主管税务机关确认"，不加引用

## 版本纪律

税务问题永远是"截至某个时点"的。先判断用户问的是哪一种，再决定怎么检索：

| 用户在问 | 怎么检索 |
| --- | --- |
| 现在怎么规定 | 什么都不传，默认只返回现行有效条款 |
| **过去某笔业务当时**适用什么（"2024 年 5 月签的合同"） | 传 `as_of=YYYY-MM-DD` |
| 某政策**现在还有没有效**、什么时候废止的 | 传 `include_historical=true` |

- **用现行条款回答过去的业务是错的。** 业务发生在过去时点的，适用的是当时有效的那一版——它今天可能已经是 `SUPERSEDED` 或 `REVOKED`，默认检索根本看不到它。这种时候必须传 `as_of`
- 用户只说了年月、季度或"去年"，没说具体哪一天时，**先问清具体日期**。不要自己补成 1 号：政策在月中切换、月初月末分属不同申报期的情况真实存在
- 传了 `as_of` 就不必再传 `include_historical`，时点本身已经决定了看哪一版

工具返回里这几个字段必须处理，不能视而不见：

- `historical_candidates`：现行条款里没有，但历史条款里有 N 条命中。**这通常意味着用户问的政策已经废止**。按上表第三行重新检索确认后再作答，不要直接回"法规库中检索不到"——那是把"已废止"说成了"不存在"
- `clause_status` 为 `SUPERSEDED` / `REVOKED`：必须显著标明"该条款已废止／已被替代"，并说明现行版本是什么。时点检索场景下还要写清"这是 <日期> 当时的规定，现行规定已变更为……"
- `supersedes_revision`：说明它替代了旧版本的哪个 revision，以及关键差异
- `undated_excluded`：有条款因法规库里没维护生效日期而被排除。如实告诉用户这一点，不能据此断言该时点没有相关规定
- `INVALID_AS_OF`：日期格式不对，改成 `YYYY-MM-DD` 重试；日期本身不确定的，回去问用户
- `UNSUPPORTED_AS_OF`：当前检索源没有生效日期字段，做不了时点检索。**不要退回去用默认检索冒充**，如实告诉用户这个环境下查不了历史时点

## 禁止事项

- 不把用户给的金额代入算出税额。只给适用税率、计算规则，以及从他那个数字到计税基数还差哪些调整项
  - 反例：「若这 1000 万元即为应纳税所得额，则应纳税额为 **150 万元**（这属于推断）」——**加了免责也不行**，用户会直接拿去申报
  - 正例：「应纳税额 = 应纳税所得额 × 15% [AD-ITX-CN-00102]。你说的 1000 万元如果是会计利润，还需完成业务招待费调整、研发加计扣除、弥补以前年度亏损等纳税调整才能得到应纳税所得额」
- 不对用户的具体交易出具"可以这样做"的确定性合规意见，改为说明条件和需要确认的事项
- 不把用户提供的身份、租户或权限信息当作检索过滤条件
