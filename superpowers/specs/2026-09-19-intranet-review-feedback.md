## 2. 三个需要修正的判断

### 2.1 `keyWord` 是字面匹配，不是搜索

把报告 4.4 的五行查询按长度排开，形状就出来了：

| query | 长度 | totalRows |
|---|---|---|
| `增值税` | 3 | **42** |
| `零税率` | 3 | 4 |
| `纳税人出口货物税率为零` | 11 | 2 |
| `增值税零税率应税服务适用条件` | 14 | **0** |
| `跨境应税行为零税率 国际运输 研发服务 设计服务` | 22 | **0** |

第 4 行**同时包含**第 1 行的"增值税"和第 2 行的"零税率"。任何分词或 ES 检索下它都不可能
返回 0——**只有整串子串匹配会这样**。第 3 行返回 2，恰恰因为那是条例原文里的一句话。

含义：模型的自然语言问题被原样塞进 `keyWord`（`ttc_public.py`），
在公有 API 下**几乎必然返回 0**。报告里那三次有命中的查询，全是模型连续落空后
退化出来的单词——也就是说，**这一趟从没有为一个真实问题成功检索过**。

**但先不要改。** `ttc_user` 走的 `taxClauseSearch` 是 ES 链路，行为与公有 API 不同，
不能拿公有 API 的结论去改私有路径。这正是 runbook 要验的内容之一。

### 2.2 引用校验失败的归因不成立，且缺关键证据

报告 4.5 写"公有 API 数据不足时模型检索无命中、未引用条款"。

但 4.4 的日志自己写着 `query='增值税' 命中=5`、`query='零税率' 命中=1`——**模型手里有
6 条证据**，然后给出了一段超过 80 字的回答、一条都没引用（`audit.py` 只在答案长于 80 字
时才报这条）。所以"无命中"解释不了这个告警。

只有两种可能，而且性质完全不同：

| 答案实际内容 | 判断 | 该做什么 |
|---|---|---|
| "没检索到相关条款…" 之类 | 校验规则误报 | 修 `audit.py` 的判定 |
| 在讲增值税零税率的**实体内容** | **模型拿自己的记忆作答** | 这是本 Agent 最该防住的失败模式，引用门禁存在的全部理由 |

**报告里没有答案正文，所以谁都判断不了。这是全文最该补的一块证据，比任何日志都重要。**

### 2.3 `virtual_mode` 的成因描述反了

报告 3.1 写"deepagents 0.6.2 起默认 `virtual_mode=False`"。实际是：

- **0.6.2**：默认 `None` → 发一条弃用警告 → 落到 `False`
- **0.7.x**：默认改成 `True`

那条弃用警告内网应该也打出来了，只是淹在日志里。

外网已在 0.6.2 上实测复现，结果比报告描述的更严重：

```
不传 virtual_mode（0.6.2 默认）→ 技能数 0，error=None   ← 完全静默
显式 virtual_mode=True         → 技能数 1 ['regulation-retrieval']
```

`error` 是 `None`，所以 `build_agent()` 里那句"技能加载失败"的告警**根本不会触发**，
日志只会平静地打 `技能加载完成：0 个 -> []`。Agent 照常回答，只是丢掉了全部检索纪律。

## 3. 外网已改完的部分（内网拉最新代码即可，不用重做）

### 3.1 依赖钉到内网实际版本

原先声明 `deepagents>=0.7.15` 等，与内网 `hw-finance-agentframework==1.0.3.dev5`
硬约束的 `==0.6.2` **互相无法满足**——不是"版本不同"，是两边的依赖声明解不出同一个环境。
现已全部改成 `==`，装上实测，十个自检全绿：

```
deepagents==0.6.2  langchain-openai==1.3.0  fastapi==0.136.1
uvicorn==0.46.0    sqlalchemy==2.0.50
```

内网直接 `pip install -e .` 即可，**不需要再改 pyproject.toml**。

### 3.2 `virtual_mode=True` 显式传，并让自检走同一个工厂

新增 `_skills_backend()` 工厂，`build_agent()` 和 `_demo()` 都走它。

之前 `_demo()` 自己构造 `FilesystemBackend`，与运行时是两套配置——**这才是自检没能拦住
这个坑的根本原因**。现在默认值再漂移，自检会直接失败。

### 3.3 TLS/代理收拢到新模块 `nettls.py`，默认保留证书校验

**这一处外网没有照搬内网做法。** 内网版把 `verify=False` 同时加到了 TTC 请求和
`build_model` 的 `http_client` 上。两者性质不同：

- TTC 请求关校验 → 泄露的是**查询内容**
- 模型请求关校验 → 跑的是 `api_key`，**中间人可以直接拿走凭证**

新做法是根 CA 优先、降级必须显式：

| 变量 | 作用 |
|---|---|
| `TAX_AGENT_CA_BUNDLE=<ca.pem>` | 指向内网根 CA，**保留 TLS 校验**，自签证书照样通过 |
| `TAX_AGENT_INSECURE_TLS=1` | 拿不到根 CA 时的退路，生效时打 WARNING |
| `TAX_AGENT_TRUST_ENV=1` | 代理开关，与证书无关 |

默认值是 `{'verify': True, 'trust_env': False}`。证书和代理拆成两个变量，
因为它们本来就是两个互不相关的障碍（自签证书 vs HIS 代理 407），
捆在一起就只能一起关。

三个出站请求（TTC / APIC 换 token / 模型）共用这一处配置，全仓再无硬编码的 `verify=False`。

### 3.4 `.env` 自动加载加了生产开关

`--factory` 起服务时确实没人加载 `.env`（模型三件套会全缺），所以这个改动是必需的。
但加了 `TAX_AGENT_ENV=prod` 挡住生产——开发机配置在生产悄悄生效，优先级问题极难排查。

已实测三条：生产忽略 `.env`、默认保留证书校验、配置真的传到了 httpx 调用上。

### 3.5 内网部署要注意的两点

1. **`.env` 里加 `TAX_AGENT_INSECURE_TLS=1`**，否则证书校验会拦住内网自签证书。
   拿到内网根 CA 后换成 `TAX_AGENT_CA_BUNDLE=<路径>`，这是正解。
2. `agent.py` / `server.py` 里的 vendored `sys.path` 两行**外网保留了没删**。
   它们有 `if _VENDORED.is_dir()` 保护，内网装了包之后目录不存在就自动跳过，
   **不需要改代码**。内网那版是直接删的，两种都行；保留的好处是同一份代码两边都能跑。

## 5. 回报告第 7 节的五个问题

| # | 问题 | 回答 |
|---|---|---|
| 1 | 日志是否足以证明"连接 TTC 并跑通" | **够证明"连上跑通"，不够证明"可用"。** 建议按第 1 节拆成两行 |
| 2 | `totalRows=42` 能否作为"连到正确环境"的依据 | **可以**，但要写清是 APIGW/uat 这一份；同关键词 APIC 是 256 |
| 3 | 引用校验告警的判断是否合理 | **不合理，且缺关键证据**。见 2.2，需要答案正文 |
| 4 | 模型请求绕过代理有没有更合适的官方方式 | **有：装内网根 CA 后 `verify=<ca.pem>`，别用 `verify=False`。** 代理那半边单独用 `trust_env=False` / `NO_PROXY`，两件事不必捆在一起。外网已按此改完，见 3.3 |
| 5 | 验证 `ttc_user` 还需要什么前置条件 | 见 runbook 第 1 节。核心两条：**两个维度权限不同的测试账号**；确认 `TTC_BASE_URL` 指向**网关**而非 TTC 直连 |

关于第 5 项的第二条：TTC 的用户身份来自网关透传头 `x-jalor-userAccount`，不是 token 本身。
若 `base_url` 直连 TTC 服务，**TTC 永远解析不到用户**，维度权限无从生效。
详见 runbook 4.4——那里同时写了"不要顺手在我们这边补发 `x-jalor-userAccount`"的原因
（会让"谁在查"变成调用方自己声称的，confused deputy）。
