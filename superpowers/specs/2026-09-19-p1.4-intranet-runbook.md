# P1.4 内网联调手册（用户身份链路验证）

> 2026-09-19。拿着这份文档进内网，从上往下做。每一步都给了命令、预期输出、
> 以及"看到别的结果说明什么"。做完把第 6 节的表填了带出来。

## 0. 这份文档解决什么、不解决什么

**要回答的唯一问题**：把真实用户的 IAM token 透传给 TTC，这条链路**通不通**，
以及 TTC 那边**认不认得出"是谁在查"**。

这是两个不同的问题，第二个才是难的那个——链路通了不代表身份解析出来了，
而且**默认的验证方法会给出假阳性**，原因见第 4 节。

**不在本次范围**：`taxClauseSearch` 缺失维度过滤的修复（TTC 侧的事，已从本次范围移除）。
本文档只验证我们这一侧的链路，不推动、不等待 TTC 的修复。

**不要做的事**：不利用维度过滤的缺口去拉越权数据。验证访问边界时**只记录条数，
不落盘条款正文**。

| # | 要什么 | 找谁 | 为什么必须有 |
|---|---|---|---|
| 1 | 目标环境（SIT/UAT）的 `TTC_BASE_URL` | 运维 / TTC | 代码里只有应用上下文 `/fin/ttc`，对外完整路径是网关映射配置，代码里看不出来 |

## 2. 步骤 0：环境准备

### 2.1 代码与依赖

```bash

# （src/tax_agent/server.py 第 23-26 行，注释里写了"内网环境删除这两行"）
.venv/Scripts/python.exe -m pip install -e .
```

### 2.2 先跑一遍离线自检，确认代码本身没坏

```bash
.venv/Scripts/python.exe src/tax_agent/auth.py
.venv/Scripts/python.exe src/tax_agent/ttc_client.py
.venv/Scripts/python.exe src/tax_agent/server.py
.venv/Scripts/python.exe src/tax_agent/audit.py
```

四行都要打印 `... self-check ok`。**没过就先别联调**——否则后面分不清是环境问题还是代码问题。

### 2.3 配 `.env`

只需要这几个（模型三件套按内网 MaaS 填）：

```
TAX_AGENT_BASE_URL=<内网 MaaS 端点>
TAX_AGENT_API_KEY=<...>
TAX_AGENT_MODEL=<...>
TAX_AGENT_LOG_LEVEL=DEBUG

TAX_AGENT_SOURCE=ttc_user
TTC_BASE_URL=<第 1 节第 1 项拿到的地址>
```

`TAX_AGENT_SOURCE=ttc_user` 是本次联调的主角：透传用户 token 调私有接口。
**不要配 `ttc_public`**——那条路用应用级凭证，没有用户身份，跑通了也说明不了任何事。

日志级别开 DEBUG：这次要看的就是链路细节。

### 2.4 拿一个真实用户 token

在内网浏览器打开法规库页面，F12 → Network → 任一请求 → Request Headers →
复制 `x-jwt-ms-token` 的值。同时记下 `x-jalor-userAccount` 的值。

**关于这个 token**：
- IAM 默认寿命约 3600 秒，过期就得重取。操作节奏按这个安排。
- **不要粘贴进仓库里任何文件**，不要写进 `.env` 之外的地方，不要提交。
- 命令行里用环境变量传，别直接写在 curl 里（会进 shell history）：
  ```bash
  read -s TOKEN   # 粘贴后回车，不回显
  export TOKEN
  export ACCOUNT=<你的域账号>
  ```

## 3. 步骤 1（链路层）：token 有没有到 TTC

### 3.1 起服务

```bash
.venv/Scripts/python.exe -m uvicorn tax_agent.server:create_app --factory \
  --host 127.0.0.1 --port 8000
```

（`create_app` 是工厂函数，`--factory` 不能省。`PYTHONPATH` 若没装 `-e .` 需要指到 `src/`。）

### 3.2 打一次真实请求

```bash
curl -N -X POST http://127.0.0.1:8000/tax-agent/chat \
  -H 'Content-Type: application/json' \
  -H "x-jwt-ms-token: $TOKEN" \
  -H "x-jalor-userAccount: $ACCOUNT" \
  -d '{"question":"增值税零税率适用条件"}'
```

> `scripts/probe_ttc.py` **这一步用不上**——它写死了 `ttc_public`，只能验应用级凭证那条路。
> `cli.py --url` 也不够：它只发 `x-jwt-ms-token`，不发 `x-jalor-userAccount`。用 curl。

### 3.3 结果怎么读

| 看到什么 | 说明 | 下一步 |
|---|---|---|
| SSE 正常流出答案，末帧 `citation_problems` 为空 | 链路通，**且网关 token 没有绑定目标服务**（不校验 audience）——这正是要证实的 | 进第 4 节 |
| 服务日志里 `TTC 返回失败：errorCode=... tracerId=...` | 请求到了 TTC，TTC 主动拒了 | 把 `errorCode` + `tracerId` 给 TTC，按 3.4 对号入座 |
| curl 直接拿到 HTTP 401，服务日志里没有 TTC 调用记录 | 我们自己的 `parse_token` 就拒了，token 格式不对或取错了 | 重取 token |
| 连接超时 / 证书错误 | 网络或 TLS 层，还没到业务 | 见 3.5 |
| 末帧 `citation_problems` 非空 | 链路通了，但模型编了条款号 | 链路验证**算通过**，引用问题单独记，别混在一起查 |

**HTTP 恒为 200**：TTC 的失败响应是 `TaxRuleFaultVO`（`{status:0, errorCode, message, tracerId}`），
HTTP 状态码照样 200。所以**不要靠 curl 的状态码判断成败**，要看服务日志里解析出来的 `errorCode`。

### 3.4 失败时的分支判断

拿到 `errorCode` 后，关键是分清三件事：

- **网关层拒绝**（请求根本没到 TTC 业务代码）→ 响应形状通常不是 `TaxRuleFaultVO`，
  更像网关的通用错误页 / `resource group cannot not found`。多半是**路径不对**，见 3.5。
- **TTC 验签失败**（token 到了但验不过）→ `TaxRuleFaultVO`，errorCode 是鉴权类。
  意味着网关签发的 token **确实绑定了目标服务**，与 TTC 的判断相反 —— 这是个重要发现，
  记下来，方案要改。
- **TTC 验签通过但无权限** → 也是 `TaxRuleFaultVO`，但 errorCode 不同。
  这其实说明链路是通的，进第 4 节。

三者的 errorCode 具体值现在猜不出来，**拿到后填进第 6 节的表**，这是本次出差的产出之一。

### 3.5 已知的两个坑

- **路径必须带 `publicservices` 段**（公有 API）。写成 `/fin/ttc/...` 会报
  `resource group cannot not found`。私有接口（`taxClauseSearch` / `queryTlpInfo`）
  的对外路径前缀**目前是未知的**——代码里按 `{base_url}/taxClause/taxClauseSearch/page/{n}/1` 拼，
  如果网关映射不是这个形状，需要调整 `ttc_client.py` 里的路径拼接。**这是第 1 节第 1 项要问清楚的。**
- **TLS 与代理**：内网自签证书 + HIS 系统代理会 407 拦截。`auth.py` 的换 token 请求
  已经写死 `verify=False, trust_env=False`；但 `ttc_client._default_post` **没有**加这两个参数。
  如果这一步报证书错误或 407，就是这个原因——在 `_default_post` 里补上同样的两个参数即可
  （`src/tax_agent/ttc_client.py:117`）。这是已知的待办，不是意外。

## 4. 步骤 2（身份层）：TTC 认不认得出"是谁在查"

**这一步是整份文档的重点。第 3 节通过了，不代表这一步通过。**

### 4.1 为什么不能用 `taxClauseSearch` 来验

直觉做法是：用户 token 调 `taxClauseSearch`，看返回结果是不是符合这个用户的权限。

**这个做法给不出结论。** 因为 `taxClauseSearch` 链路（`taxClauseSearchESParamProcess`）
**今天根本没有维度过滤**——入参原样透传 ES。也就是说：

- "TTC 正确解析出了用户，但这个接口不做维度过滤" → 返回全量
- "TTC 压根没解析出用户" → 也返回全量

**两种情况返回一模一样。** 用它来验身份，等于用一把坏了的尺子量长度。

### 4.2 为什么必须两个账号

即使换成有维度过滤的接口，单账号也证伪不了：你看到 500 条，无法判断这是
"你的权限范围就是 500 条" 还是 "没做过滤，全库就 500 条"。

**必须两个维度权限不同的账号，比对结果集。** 这就是第 1 节第 4 项的由来。
拿账号时要跟业务确认："这两个账号在法规库页面上看到的条文范围是不一样的"——
如果他们也说不准，让他们各自登录页面搜同一个词，看总数是否不同。

### 4.3 决定性测试：`queryTlpListByES` 双账号比对

`queryTlpListByEs` 链路（`invokeClauseEsApi`）**今天就有完整的维度过滤**
（`setJuDimension` 交集、无权限返回空）。用它来验。

**注意这不是我们代码在调的接口**，所以这一步**直接 curl 打 TTC**，不经过我们的 Agent：

```bash
# 账号 A
curl -s -X POST "$TTC_BASE_URL/taxClause/queryTlpListByES/page/100/1" \
  -H 'Content-Type: application/json' \
  -H "x-jwt-ms-token: $TOKEN_A" \
  -d '{"keyWord":"增值税"}' | head -c 2000

# 账号 B（同样的关键词）
curl -s -X POST "$TTC_BASE_URL/taxClause/queryTlpListByES/page/100/1" \
  -H 'Content-Type: application/json' \
  -H "x-jwt-ms-token: $TOKEN_B" \
  -d '{"keyWord":"增值税"}' | head -c 2000
```

> 入参是 `TaxClauseParam`，吃 **`keyWord`（大写 W）**，不是 `keyword`。
> 这个接口和 `taxClauseSearch` 的入参名不一样，别抄错。
> 响应是 `PagedResult<TaxClauseVO>`，看 `totalCount` 或等价的总数字段。

**结论判定**：

| 两个账号的总数 | 结论 | 含义 |
|---|---|---|
| **不同** | ✅ TTC 解析出了用户身份，维度过滤生效 | 方案成立。我们把权限完全委托给 TTC 这件事是真的 |
| **相同** | ⚠️ 两种可能，要继续区分 | 见下 |
| 某个账号返回空 | 该账号无任何维度权限 | 换账号，或确认这是预期 |

总数相同时，继续区分：
1. 先确认两个账号的权限**确实**不同（回 4.2，让业务在页面上验一次）；
2. 权限确实不同而结果相同 → **TTC 没有解析出用户身份**，走 4.4。

**只记总数，不要把返回的条文正文落盘。**

### 4.4 如果身份没解析出来：原因和正确的修法

大概率原因是：**TTC 的用户身份来自网关透传头 `x-jalor-userAccount`，不是 token 本身。**
TTC 认的是 `RequestContext.getCurrent().getUser().getUserAccount()`，这个 `UserVO`
由网关的过滤器构造。我们的 `UserTokenProvider`（`src/tax_agent/auth.py:36`）
**只发 `x-jwt-ms-token`，不发 `x-jalor-userAccount`**——这是有意的。

于是链路形态决定成败：

- **`TTC_BASE_URL` 指向网关** → 网关验签 `x-jwt-ms-token` 并注入 `x-jalor-*`，身份成立。
- **`TTC_BASE_URL` 直连 TTC 服务** → TTC 拿不到 `x-jalor-userAccount`，**永远解析不到用户**。

**正确的修法是把 `TTC_BASE_URL` 指向网关**，不是在我们这边补发 `x-jalor-userAccount`。

> ⚠️ **不要顺手"修好"它。** 把收到的 `x-jalor-userAccount` 原样转发给 TTC 看起来只差一行代码，
> 但那会把"谁在查"变成调用方自己声称的——任何能直连到我们服务的人都能冒充任意账号
> （confused deputy）。只有在**网络层能保证只有网关可达我们的服务**、且 TTC 与安全同意的
> 前提下才能这么做，这是个需要拍板的决策，不是联调现场能定的事。
> 现场发现是这个情况，就**记录下来带回来**，第 6 节有对应栏位。

## 5. 步骤 3：顺手采集（都需要真实环境，一趟做完）

这几件事单独跑一趟内网不值得，和上面一起做掉：

### 5.1 过期 token 的真实响应（**优先级最高**）

等手里的 token 过期（或拿一个已经过期的），重放 3.2 的请求，**把完整响应体抄下来**。

为什么重要：HTTP 恒 200，**无法靠状态码区分"token 过期"和"没有权限"**。
需要一个确定的 `errorCode` 作为"请用户重新登录"的判定键，否则过期只能报成通用失败。

抄下来的是 `errorCode` 和 `message`，**不是 token**。

### 5.2 排序能不能覆盖

`taxClauseSearchESParamProcess` 显式设了 `sortField=TLP_NUMBER, sortOrder=ASC`。
试试请求体里带 `sortField` / `sortOrder` 能不能覆盖：

```bash
-d '{"keyword":"增值税","sortField":"ES_SCORE","sortOrder":"DESC"}'
```

（注意：`taxClauseSearch` 吃的是 **`keyword`**，小写 w，和 4.3 那个接口相反。）

**即使能覆盖，本地重排也不拆**——`es_score` 没有映射进 `TaxClauseVO`，
拿不到分数就没法信任服务端的相关性序。这一项只是把"能不能"记下来。

### 5.3 `effectiveState` / `archiveFlag` 的真实取值分布

搜几个词，把返回里这两个字段出现过的值统计一下（只记值和出现次数，不记正文）。
验证 `ttc_client._clause_status()`（`src/tax_agent/ttc_client.py:40`）的映射假设：
`archiveFlag=Y`→SUPERSEDED、`effectiveState=EXPIRING`→REVOKED、
`SOONTOEXPIRATION`→按现行处理。**出现没见过的值就记下来**，映射要补。

### 5.4 税种字典接口通不通

```bash
curl -s "$TTC_BASE_URL/taxFoundation/taxBaseData/getAllTaxCategory" \
  -H "x-jwt-ms-token: $TOKEN"
```

这个接口在 **`trcFoundationService`**，是**另一个服务**，需要单独的网关暴露——
很可能打不通，打不通是正常结果，记一下即可。通了的话把全集抄回来，
个人所得税 / 印花税 / 关税归在哪个 `taxCategoryCode` 目前是猜的。

## 7. 一句话总结

第 3 节验的是"**通不通**"，第 4 节验的是"**认不认得出你是谁**"。
第 3 节容易过，第 4 节容易给假阳性——**没做双账号比对，就没验过身份链路**。
